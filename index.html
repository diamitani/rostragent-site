Why Rostr

Other frameworks make you program the team.
Rostr compiles it.

Frameworks like CrewAI ask you to define every agent's role, write every task, and wire the crew together in code. That is programming, not delegating. Rostr takes the opposite approach: you describe the outcome in plain language, and the system builds the team for you.

The programmed team

  • You define each agent's role and backstory
  • You write every task by hand
  • You wire the sequence and handoffs in code
  • You build your own state, memory, and retries
  • Every new product means a new wiring job

The compiled team

  • You describe the goal in one paragraph
  • PAL turns it into a structured work order
  • NPAO triages and orders the tasks
  • The runtime staffs specialist workers and verifies their work
  • The hub keeps shared state; the context engine remembers across sessions

Rostr is not a wrapper around other frameworks. It is its own runtime, designed around one idea: the person asking for the work should not have to manage the workers.

How it works

From one paragraph to finished work.

Every run through Rostr passes through the same five stages. You write the first line; the system handles the rest.

01

PAL — the work-order compiler

Prompt Assembly Language takes your plain-language goal and compiles it into a structured work order: tasks, the skills each task needs, and the rules the workers must follow.

02

NPAO — the triage desk

Needs Prioritization and Ordering looks at the work order, decides what matters most, and sequences the tasks so nothing important waits behind busywork.

03

Runtime — the staffing office

The runtime staffs each task with a specialist worker, runs them, checks their results, and retries once when something comes back wrong. Built once, deployed once, shared by every project.

04

Hub — the shared memory

Every worker reads from and writes to the same state: progress, decisions, and reference material. Nothing gets lost between tasks, and nothing is duplicated.

05

Context engine — the long memory

A background loop watches every session. When the context window fills or time passes, it saves the session, compresses it, and files it in a master library. Next session picks up where the last one left off.

Product anatomy

Five layers. One runtime.

Rostr is a stack, not a script. Each layer has one job, and each one is replaceable without touching the others.

L1

Runtime

One shared API, deployed once. Agents are definition files, not separate programs. Your app calls the API; the runtime does the rest.

L2

Orchestration

PAL and NPAO: the compiler and the triage desk. Plain language in, ordered work out.

L3

State

The hub. Shared, persistent state for every run — progress, decisions, references — namespaced by project.

L4

Tools

Generic tools through Composio, proprietary tools through your own hosted MCP servers. Skills stay portable markdown.

L5

Reference

The context engine (session memory) and RAG DAL — the research layer that ingests URLs and documents, scores sources by tier, and refuses to guess when it finds nothing.

The API

This is the whole integration.

Your app sends a goal. Rostr streams back finished work. No agent definitions, no wiring, no orchestration code on your side.

POST /api/v1/run 
curl -X POST https://api.rostr.dev/api/v1/run \
  -H "Authorization: Bearer YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "project_id": "artispreneur",
    "goal": "Build a press kit for Maya Reyes: bio, photos, tour dates, streaming links."
  }'

# The response is a stream of finished work:
# event: task_started   {"task": "Draft artist bio"}
# event: task_done      {"task": "Draft artist bio", "verified": true}
# event: task_started   {"task": "Collect streaming links"}
# event: task_done      {"task": "Collect streaming links", "verified": true}
# event: run_complete   {"artifacts": ["epk/maya-reyes.html"]}

Models are selected per task through the AI gateway — Claude or OpenAI — without changing your code or your skills.
